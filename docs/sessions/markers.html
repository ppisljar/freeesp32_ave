Stimulus markers

A session makes light and sound. A marker makes a timestamp — the announcement that something meaningful just happened, delivered to whatever else is recording. Without one, an EEG trace and the stimulus that drove it are two files with no way to line them up.

The problem markers solve

Picture a twenty-minute session: ten-hertz flicker, a ten-hertz binaural beat, a glide down to six hertz, then a return. Alongside it, an EEG is recording brain activity.

The EEG has no idea when any of that happened. It has a continuous signal and no boundaries. You cannot ask whether the response grew after the light came on, how fast it settled, or whether it returned to baseline afterwards — because you do not know where "after the light came on" is in the recording.

A marker is that boundary, written into the record:

Session timeMarkerMeaning
0 msSESSION_STARTexperiment begins
5,000 msBASELINE_STARTno stimulation
35,000 msLIGHT_ON10 Hz LED starts
65,000 msAUDIO_ONaudio added
95,000 msGLIDE_STARTrate begins changing
185,000 msSESSION_ENDcomplete

M lines

M <time_ms> <LABEL> [key=value ...]

A new line type, scheduled by the same timeline that runs the light and the sound. Nothing about the existing syntax changes.

# Begin with a baseline
M 0      BASELINE_START

# Start 10 Hz stimulation
M 30000  STIM_START      condition=alpha10 block=3
30000 10 50 60 0 0 255 15

# Change condition
M 60000  CONDITION_CHANGE condition=audio_visual

# End the trial
M 90000  STIM_END
FieldRules
LABEL[A-Z0-9_], 1–31 characters. An out-of-charset label is rejected, not sanitised — these strings become event names in an analysis script, and an event silently renamed by the firmware is not recoverable from the data.
key=valueUp to four pairs; key ≤15 chars, value ≤31. A token with no = is warned about and skipped.
mod=Reserved. Sets the modality (below) rather than inferring it. Never stored as a key/value pair.

SESSION_START and SESSION_END are emitted by the firmware when your file does not carry them, so a recording always has its boundaries.

Three timestamps, and why they are not one

This is the part worth reading twice. Every marker carries three times, and treating them as interchangeable is the error the whole design exists to prevent.

FieldMeaning
t_sched_uswhen the .ledc intended the event
t_disp_uswhen the firmware processed it
t_onset_pred_uswhen the signal is expected at the output

The third is predicted, not measured. It is t_disp_us plus the modality's pipeline latency, and it is named ..._pred_us in the struct, the JSON, the log and the API so that it cannot quietly be read as a verified onset.

A marker timestamp is not a verified physical onset. If the difference matters for your experiment, validate the GPIO sink against a capture rather than trusting the prediction.

The latencies come from the device's measured audio/LED synchronisation:

  • audio — 46.439 ms, the 8 × 256-frame I2S DMA ring.
  • LED — that same anchor plus the strip write, at led_count × 30 µs (1.25 µs/bit × 24 bits per pixel). The midpoint is used, which on a 74-pixel strip leaves about ±1.1 ms of honest uncertainty: a zone's pixels are scattered along the serial chain, so the honest answer is a range, not a number.

Measured on hardware, dispatch runs 0.5–0.6 ms behind schedule, and predicted onsets land at dispatch + 46.439 ms (audio) or + 47.549 ms (LED).

Modality is inferred, so you need not think about it

A marker takes its modality from whatever shares its timestamp: beside an LED row it marks an LED event, beside an audio row an audio event, beside both it uses the later lag. Override with mod=led, mod=audio, mod=both or mod=none (none being bookkeeping only — predicted onset equals dispatch).

Markers are stamped with the batch's dispatch time rather than the instant the executor's third pass reaches them, so a marker and the stimulus it announces share one reference.

Checking a marker without the hardware

The browser simulator resolves M lines the way the device does and shows them in its timeline inspector: the modality it inferred (and that it was inferred rather than stated), and the predicted onset for that modality. It draws them on the scope too — a solid tick at the scheduled time and a dashed one at the predicted onset, so the gap between the two is visible rather than arithmetic.

Markers also occupy a slot in the device's 100-entry timeline, which is easy to forget because they produce nothing you can see or hear. Both the browser's entry counter and sessions/validate_session.mjs count them.

Sinks: a list, not a fixed set

Configured on the Settings page. Every enabled sink receives every marker, and several of the same type are allowed — two UDP destinations for two recording machines, or two GPIO pins for two marked modalities.

GPIO — a TTL pulse

The lowest timing uncertainty, and independent of WiFi. Pin, pulse width and active level are configurable, plus when it fires:

  • onset (default) — scheduled for the predicted physical onset, so the pulse lines up with photons and sound rather than with the parser.
  • dispatch — fires immediately. Useful for measuring the difference between the two, which is the only honest way to check the prediction.

Never connect this pin to an EEG electrode, or to an input that is not designed for a digital trigger. The recorder must support a trigger input electrically. Use opto-isolation if there is any doubt — see the hardware section.

UDP — into research software

One JSON object per datagram. tools/lslbridge/ turns that stream into a Lab Streaming Layer marker stream, which LabRecorder can record into an XDF alongside the EEG.

The bridge maps the device's monotonic clock onto LSL's with periodic round-trip offset estimation. Timestamping on arrival is not good enough for precise work: the variation in network delay would land directly in your marker times.

SD card — reproducibility with nothing attached

Appends JSONL under the card root, opening with a provenance header:

{"rec":"header","session":"session","session_sha256":"f522ea9a…",
 "fw_elf_sha256":"0b8bc44f6af6a1c6","origin_mono_us":…,
 "pipeline":{"audio_lag_us":46439,"led_lag_us":47549,"led_count":74,
             "note":"onset times are PREDICTED from these lags, not measured"}}
{"rec":"marker","seq":3,"label":"AUDIO_ON","t_sched_us":3000000,
 "t_disp_us":3000533,"t_onset_pred_us":3046972,"modality":"audio"}
{"rec":"footer","markers":6,"dropped":0,"max_sched_disp_delta_us":611}

The firmware ELF hash and the session-file SHA-256 are there so a log can be tied to the exact firmware and the exact session that produced it. "I think it was that version" is not a basis for a reproducible experiment.

Dropped markers are counted, never silent

Markers are queued into a preallocated ring and written out by a low-priority task — nothing touches the card or the network from a dispatch path. If that ring overflows, the count reaches the log footer and /api/state. A marker that silently never existed is the one failure that quietly invalidates a recording, so it is always reported.
