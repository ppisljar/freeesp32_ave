Complete .ledc reference

Every line type, every column, every accepted value, every default, every range and every interpolation prefix. This page mirrors ledc_format.md revision v3, which was itself written by reading main/config_parser.c line by line. Where this page and the device disagree, the device is right and this page is a bug.

A must be its own token. parse_line tests only the first character and then hands the remaining tokens to the audio parser, so A1500 200 0 50 0 discards A1500 entirely: the line executes at t=200 ms with freq 0, pan 50, and every field shifted left by one. The linter flags it as LEDC_AUDIO_GLUED_TIME (warning). Lower case a, s and bg all work. S is recognised only as a one-character token; anything else that is not A/a/ S/s/BG falls through to the LED parser.

The legacy 5-token LED line is time freq duty bright mask. It sets RGB to full white explicitly (so it is directly comparable with an 8-token white line) and it cannot carry any pulse column.

The 50-per-timestamp cap is the one device limit with no runtime diagnostic, which makes it worth remembering: the "find the next strictly later timestamp" scan walks straight past the leftovers. The linter reports it as LEDC_BATCH_CAP (error) — that is your only warning.

Ordering and dispatch

Entries are stable-sorted by time at parse (config_parser_parse_content), so authoring order within one timestamp is preserved and grouping your file by layer rather than strictly by time is safe.

Each timestamp then dispatches in three passes — all audio, then all LED, then everything else — so audio channels armed in the same batch start phase-coherent. That is what makes a monaural pair or an antiphase LED pair share a predictable initial phase: put both halves on the same timestamp.

The first batch is hoisted. It fires at wall-clock 0 whatever its timestamp. That is benign for LED, which is anchored to the demanded time, and not benign for audio, which starts at dispatch. The linter reports it as LEDC_FIRST_BATCH_HOIST. Start your files at t=0.

The three rate regimes — freq > 0, freq 0, freq < 0

freqMeaningWhat the LEDs do
> 0flicker at that ratesquare / env-shaped pulse train
0DC channelsteady on at the row's bright and RGB — no flicker
< 0stop the maskchannel goes inactive; the timer is torn down if no channel is left

A DC channel is a real feature, not a degenerate case: nineteen shipped sessions use it (05_focus_smr holds its lamp at 0 Hz for the whole run, 31_ganzfeld_amber is a Ganzfeld field). The ISR has a dedicated branch for it (led_matrix_example.c:824) that still evaluates brightness and colour ramps and modulations every tick, so a DC channel can breathe and fade — it just never gates off.

  • To turn a channel off, write a negative rate — -1 is conventional. A row of 0 leaves the channel active, which keeps the flicker timer alive and therefore pins the ISR tick where it was.
  • bright 0 with freq 0 is dark but still active. Fine as a final row (the end-of-timeline handler stops everything anyway), not as a mid-session off switch.
  • A rate ramp that crosses zero is unrenderable below it. > interpolates linearly toward the next entry's rate, so a descending glide whose target is a negative stop row sweeps the demanded rate down through 0 and into negative territory. Pin the ramp with a plain row at its intended endpoint before stopping the channel.

/api/state reports audio channels 1-based. The state handler emits "ch": i + 1, so .ledc ch 8 appears there as ch9. This has already cost measurement time; convert once and write it down.

BG — background audio

BG <url> <pan> <loudness>

BG is a session-level annotation, not a timeline entry. It is intercepted before parse_line, never occupies an entry slot, and last one wins (with a warning). Accepted schemes: http://, https://, sdcard://, push://. pan is clamped to ±100 and loudness to 0–100 (parse_bg_line).

A push:// URL makes the executor hold the timeline until the stream has buffered or a timeout fires, which moves t=0. Do not use it in anything whose timing you intend to measure.

S — speech

S <time> <voice> <volume> "<text>"

S is not browser-only. The device parses it always, and plays it when the firmware is built with CONFIG_BG_SDCARD_ENABLED (set in sdkconfig.defaults.esp32s3); without that option the entry parses, occupies an entry slot, and does nothing. voice defaults to default and volume to 80 if unparsable. The text is read from the raw line between the first and the last ", so inner quotes survive and a trailing comment is ignored.

The browser strips S rows before POSTing, and the analysis tooling strips them too unless you pass --keep-speech.

The - sentinel and absent trailing columns

0    40 25 80 0 128 255 1  1 0            # ch1: 40 Hz, sine env, duty 25, phase 0
0    40 25 80 255 160 40 2  1 180         # ch2: same, phase 180 -> antiphase (invisible)
5000 -  -  -  -   -   -  1  -  -  - 0.3   # ch1: change ONLY jitter; keep everything else

One rule, two spellings. A field written -, and an optional trailing column left off entirely, both mean "leave this channel's value unchanged". The parser records what the line actually set in entry->present; the executor substitutes the channel's live value for every bit that is clear. A cleared bit is never treated as 0.

A negative number is unaffected: the sentinel test requires the token to be exactly one character, so -50 still parses as minus fifty.

That rule now holds for every optional trailing column. The one place it was broken was audio waveType, where an omitted column used to reset the channel to sine; the parser now reads the live waveform back instead. Four caveats remain, and they are not sugar:

CaveatDetail
1. mask and ch are selectors, not values - in the LED mask column parses as 0 and the whole line is rejected. - in the audio ch column selects channel 0. There is no "current channel" to leave unchanged.
2. At channel start there is no live value to keep For audio, the substitution only happens when the channel is already active and the entry is on the timeline path; otherwise the parsed zero stands, so - on freq or vol in a channel's first entry means literally 0. For LED the live value comes from led_matrix_get_snapshot, and an inactive channel reports freq 0 — so - on freq in a first entry resolves to 0, which is a DC channel (steady on), not a stop (lint LEDC_DASH_FREQ_STOPS). Write a negative rate to stop a channel.
3. LED - reads the lowest bit in the mask A multi-bit mask whose channels hold different live values collapses them all to the low bit's value for every - field.
4. A ramp target is read from the next entry's struct member, not its present bit …for the core fields. So a > pointing at an entry that writes - for that field ramps to 0, not to "hold" (lint LEDC_RAMP_TO_ZERO, error). The pulse fields — duty, phase, attack, freqR, depth — do it correctly: they scan forward for the next entry that actually sets the field, and hold if there is none.

A glyph on an env column is parsed and silently discarded by design (parse_v2_enum). On mask or ch it corrupts the value.

freqR and depth take > and * only. A periodic glyph on either is accepted by the tokenizer but not implemented: the parser logs a warning, drops the interpolation, and holds the start value. Everything else about them is a normal compound cell.

Animate-on-start. The glyph lives on the entry where the ramp begins, and the target value comes from the next entry. A 0 >200 … followed by A 8000 400 … glides 200→400 Hz over eight seconds. A ramp written on the last entry of a channel never fires (lint LEDC_ORPHAN_RAMP).

A ramp on a running channel starts from the LIVE value, not from the literal in the file (audio_generator_start_sweep_locked, led_matrix_start_sweep_masked). That is deliberate — starting from the literal snaps audibly when a previous ramp was interrupted — but it means a file whose literal disagrees with the live state is lying to its reader. Write the live value. The linter flags the mismatch as LEDC_RAMP_START_SUBSTITUTED (info).

For the audio pulse fields (duty, phase, attack) the start value is the literal — except duty 0, which the setter refuses, so a >0 duty ramp silently starts from the previous duty.

Ranges, and which path enforces them

The guards are not in the parser — they are in the engine, and until recently they were on only one of the two dispatch paths.

LED. The no-sweep path (taken when the entry carries no >/* field) rejects freq > 100, duty > 100 and bright > 100. The sweep path validated nothing, so identical values executed unchecked whenever the entry carried a ramp; the same three guards now apply there too, checking both endpoints of every ramp.

An out-of-range LED entry is dropped, not clamped. The install returns ESP_ERR_INVALID_ARG, the error is logged, and those channels get neither the sweep nor a fallback flicker — they keep doing whatever they were doing.

One hole remains: LED duty and bright are cast to uint8_t at parse time, before any guard sees them. 101–255 is caught by the guards, but above 255 the cast wraps (300 → 44) and the guard then sees an in-range value. Nothing warns. R G B are safe — clamp_u8_field clamps and logs.

Audio — freq and vol are clamped on the session path; pan is not. The validating entry points (which reject freq ≤ 0 or > 22050, amplitude outside 0–1, pan outside ±1) are the non-_locked wrappers, and no session path calls them: the timeline batch executor and /api/patch both hold the mutex and call the _locked variants, which clamp freq and amplitude — rather than reject them — at every entry point, including both ends of every ramp. Clamping rather than rejecting, because rejecting would silence a channel mid-session over one bad row.

What out-of-range audio values actually do from a .ledc file.
You writeWhat happens
vol 500Clamped to vol 100 (amplitude 1.0). Worth knowing why the ceiling matters: vol is divided by 100, so an unclamped vol 10000 would reach the mixer as amplitude 100 — still 6.25× full scale even after the 1/16 divisor, into headphones.
pan 200Still unguarded. The equal-power law runs past 90°, so the left output inverts polarity while the right falls back toward 0.707. Keep pan inside ±100.
freq 30000Clamped to 22050 (Nyquist), so it cannot alias.
freq 0, sineSilence — but the channel stays active. An audio line never stops a channel; use vol 0. Deliberately not clamped away: freq 0 is also how the noise wave types run.
freq 0, squareA constant +1.0, i.e. a DC offset on the output, because the phase never advances.

Note the asymmetry: an out-of-range LED entry is dropped, an audio one is clamped. That is deliberate — a dropped LED row is visible, whereas a dropped audio row means silence where the session expects a carrier. The linter models the LED guards (LEDC_LED_OUT_OF_RANGE, LEDC_LED_REJECTED); it does not flag audio values the firmware will clamp, nor pan outside ±100.

env — the pulse envelope

Set per entry, never ramped. Every behaviour, including each line type's legacy, is an explicit value.

envShapeUses duty?Uses attack?Default depth (audio)Available on

When the column is absent you get the line type's legacy value: LED → 0, audio → 4. An out-of-range value falls back differently on the two paths — LED to 0, audio to 4.

duty is ignored by env 1 and env 2, on both paths. iso_gate() returns 0.5 − 0.5·cos(2πph) for env 1 and a fixed symmetric ramp for env 2, neither of which reads duty; led_carrier_level_iram() reads duty_q16 only in its trapezoid branch. So:

  • a duty column alongside env 1 or env 2 is a silent no-op;
  • a duty modulation alongside them is also a silent no-op — the modulation engine dutifully animates a value nothing reads;
  • env 2's on-fraction is always exactly 50 %;
  • env 1 measures an apparent duty of 66.67 %, which is just the fraction of a raised sine above its own mid-level.

If duty matters, use env 0 or env 3. Measured accuracy there: a commanded 25 % / 75 % reads 25.08 % / 75.03 %, with a gate rate of 8.0107 Hz against a commanded 8.000.

Both sine envelopes are true raised sines, not the 4x(1−x) parabola their comments used to advertise. The parabola has a derivative discontinuity at the cycle boundary, so its harmonics fell as 1/n²: an 8 Hz alpha gate was simultaneously driving 16 Hz at a quarter of the fundamental and 24 Hz at a ninth — beta content inside an alpha session. The LED path measured 0.286 / 0.145 before its fix and the audio path 0.251 / 0.112, which is how we know it was literally the same shape.

Measurement note. The fifth harmonic of a 10 Hz flicker lands on 50 Hz, so mains-hum pickup shows up there and is easy to mistake for real harmonic content. Check whether h5 moves when you change the flicker rate.

depth — audio pulse depth

The fourteenth audio column. A compound cell, 0–100 %, appended last so every existing file keeps its column positions. It is how far the gate pulls the carrier down:

unipolar gates (env 0..3):   sample *= (1 - depth) + depth * gate
bipolar tremolo (env 4):     sample *= 1 + depth * sin(mod_phase)

On a gate, 100 = the carrier reaches silence between pulses (a true isochronic tone) and 0 = no modulation. On env 4 it is the classic tremolo index.

Default when the column is absent depends on the envelope, because the two families want opposite things. Source: execute_timeline_entry_ctx and audio_generator_set_iso_channel.
env columndepth columnEffective depthWhy
absentabsent10 %Legacy: no override is set, the generator falls back to params.mod_depth = 0.1, and pre-column files are byte-for-byte unchanged.

anypresentthe columnClamped 0–100 at parse.

Three things to plan for when you turn depth up:

  • Full depth is quieter. A 50 %-duty gate at depth 100 is −3.01 dB in mean power against the same tone ungated — the carrier really is off half the time. Perceived loudness drops with it, so vol usually needs raising. (At the old 10 % depth the difference was about 0.2 dB, which is why nobody noticed.)
  • Full depth on a square gate makes clicks by construction — a step discontinuity at every edge. The click-free route to full depth is env 3 (trapezoid) with attack 3–10 ms, which rounds both edges; the trapezoid additionally clamps the edge to half the on-time, so a short gate degrades to a triangle rather than misbehaving.
  • depth 0 now genuinely means "no modulation". The generator uses a negative "unset" sentinel (iso_depth initialised to -1.0f, tested with >= 0.0f), so a written 0 is honoured and the modulation is removed. Writing mod 0 also removes modulation, and is unambiguous either way.

jitter — anti-habituation wander

One token, <amp> or <amp>:<period_ms>. 0 or absent means off. Amplitude is in hertz; period is the full cycle, defaulting to 45 000 ms. The two line types do genuinely different things.

LEDAudio
Scopeper channel-maskGLOBAL — the setter takes no channel argument

Shapebipolar triangle LFObipolar sine LFO

Three consequences on the audio side: the last audio line in the file carrying a jitter column sets it for the whole session; a channel that sets no jitter column still wanders if some other line turned it on; and a mono channel never wanders at all, because the offset is only ever added to the right carrier. It never touches the isochronic mod rate — to wander a pulse rate, put a ~ or ^ modulation on mod instead.

Both jitter globals are reset to their defaults at session start and session stop, along with the rest of the pulse shape (env/duty/attack/depth, the flicker carrier) and the LED channels' retained freq/duty/bright/RGB. A session never inherits shaping from the one before it, so there is no need to write jitter back to 0 at the end of a file.

"Absent = leave unchanged" applies within a session. The baseline each session starts from is always the documented default.

A jittered LED channel is also excluded from the cycle-lattice re-anchor, by design — there is no fixed lattice to snap to.

phase is a LEAD, not a lag

The firmware adds phase × period / 360 to elapsed time, so the edge arrives earlier — matching sin(ωt + φ) rather than "start this many degrees later". The audio side adds a phase offset to the mod accumulator, which is the same sign convention.

0 and 180 are symmetric under negation, so they are identical either way — and across sessions/library the phase column takes only those two values (265 occurrences of 0, 210 of 180). To delay by N degrees, write 360 − N.

Provenance: the four numbers are corroborated in sessions/test/README.md (t06), but no report file holds the raw capture, so they are corroborated rather than re-derivable from the tree. The sign convention itself is verifiable in led_flicker_timer_callback (eff_elapsed += off).

Audio phase is per channel and stored as a fraction of the mod cycle, so it is frequency-independent by construction and survives mod ramps. LED phase is applied at use-time from the live period, so it stays a fixed phase through frequency ramps. 180 on one channel of a complementary-colour pair sharing a start time gives antiphase, hence luminance-flat "invisible" flicker — the LED carrier shapes are luminance-linear with no perceptual gamma specifically so that a 180°-antiphase pair of raised sines sums to a constant.

attack — trapezoid edge width

Milliseconds. Only env 3 reads it. Negatives become 0. It defaults to 3 ms on a fresh LED channel and 3 ms on a fresh audio channel. Click-safe is 2 ms and up.

The upper cap is path-dependent.

So a ramped LED attack can exceed a stepped one in the stored and reported state while rendering identically above 60 ms. If you need a long edge, what you are really asking for is env 1 (sine).

Wave 7 is a non-geometric single-cycle lookup table — a "replicated EEG waveform". It is a carrier and needs a valid frequency; it is not noise. The code is careful about that in two places: the is_noise test that waives the frequency check is a range test over white…brown, written that way specifically so 7 falls outside it; and the carrier scaling likewise leaves 7 unscaled by the noise level factor, so an EEG channel is about 6 dB hotter than a noise channel at the same vol. Its binaural beat comes from L/R detune exactly like sine's, because both ears read the same table at their own phase.

Caveat: the frequency check that waiver belongs to lives in a function no session path calls, so in practice an EEG, sine or square channel written with freq 0 is not rejected — the phase simply never advances and the channel emits a constant. Silence for sine, a full-scale DC offset for square, and for EEG whatever the table's first entry holds. Noise channels (4, 5, 6) are the only wave types for which freq 0 is meaningful.

bright and the drive curve

Light output is proportional to bright × RGB/255 — the "effective drive" — but only in the upper part of the range.

Above drive ~100 it is linear to about ±1 %. Below that it rolls off, reaching 68 % of linear at drive 12. This is the LED's own behaviour at low PWM, not a firmware scaling bug — validated as a device property rather than a sensor artifact by two sweeps at different RGB (255 and 60) that overlap in effective drive (48 / 51 / 60) and land on the same curve there.

It matters because therapeutic sessions live in exactly that region, and because the roll-off is uneven, so a dim brightness LFO is distorted in shape and not merely shallow. If an accurate low-brightness ramp matters, raise the RGB value and lower bright to hit the same light at a higher effective drive. See the photic page.

The mixing model — why vol is an absolute quantity

audio_generator_fill_buffer scales every channel by a fixed 1 / NUM_AUDIO_CHANNELS = 1/16 = −24.1 dB, unconditionally — never by the number of channels that happen to be active.

Think of sixteen violins in a room. Each has its own volume. Maximum loudness is all sixteen playing at once. If fifteen stop, the remaining one does not get louder. That is exactly the model: per-channel vol is an absolute quantity, not a share of a mix, and it is a hard overflow guarantee that cannot click when channels start or stop.

The cost is level. Measured device-side int16 peaks with audio_max_volume at 100.
ChannelPeak at vol 100Why
Single centre-panned sine−27.1 dBFS (int16 peak 1448)1.0 × 0.7071 for the equal-power pan law × 0.0625

About 4 of the 16 bits go unused, which is why brown noise's high-frequency tail sits near the quantisation floor. This is deliberate, not a bug, and it is also not currently adjustable from a session. A replacement divisor of 1/max(1, n_active) has been proposed and deliberately not applied, because every existing session would get up to 24 dB louder on a head-worn device. Downstream of the divisor there is one more gain — the runtime audio_max_volume setting, 0–100 % — and then a hard clamp to ±1.0 before the int16 conversion.

Practical consequence: vol above 100 is accepted and works, and is the normal way to pay for a deep gate or a quiet carrier. See ranges.

Binaural: two idioms, and pan does nothing in one of them

  1. One channel with freqR set. The generator drives the left carrier at freq and the right at freqR and routes them straight to L and R — "binaural bypass". When frequency_r > 0 and frequency_r ≠ frequency, the pan stage is skipped entirely, so pan has no effect on such a channel. (The equal-power law would cross-mix the two carriers between ears, and at any non-centre pan attenuate one to zero and collapse the beat.) Balance the ears with two channels instead, or with vol.
  2. Two channels hard-panned −100 / +100 with slightly different carriers. Both go through the normal pan law, so each ear gets its own carrier and more than 40 dB of separation from the other's.

Either way the beat is the frequency difference between the two spectral lines. Nothing in the recorded signal beats, so never look for a beat line in a mono sum.

freqR is absolute, not a detune offset. Ramping it with > or * is the direct way to glide a beat and now works — a bare atof(">250") used to evaluate to 0.0 and silently collapse the channel to mono, which for a binaural device is the worst possible failure mode (lint LEDC_FREQR_PREFIX, error, now a false positive). The older idiom — ramp the left carrier and leave freqR pinned — still works and is what the shipped library does; the beat moves because freqR is absolute.

Because freqR is absolute and "absent" means "keep the live right carrier", an entry that moves freq and omits freqR can turn a mono channel into an unintended binaural pair. See item 7. Restate freqR — 0 for mono — whenever you move an audio carrier.

Path-dependent behaviour worth knowing

Every one of these has cost somebody a measurement session. They are observations about the code, not format rules.

  1. A fresh LED start re-latches env, attack and jitter from module-global defaults. The flicker start writes the carrier waveform (square), attack_ms = 3 and the jitter globals unconditionally, and the timeline calls it for any mask that is not already fully active (the "is flickering" test is ALL, not ANY). So a row that restarts a channel after a freq < 0 stop, or a multi-bit mask where one bit is idle, resets env/attack/jitter to the defaults on every bit in the mask unless the row restates them — defeating "absent = leave unchanged" for those three columns. phase survives (it is not re-latched), and the sweep path does not re-latch at all, so whether the reset happens depends on whether the row carries a ramp. Restate env on every row that restarts a channel. Not covered by a lint.
  2. A fresh channel started via the sweep path gets attack 0, not 3 ms — the sweep install never reads the attack default and the static initialiser leaves it at 0. Only matters for env 3.
  3. A stepped audio duty 0 is a no-op — the setter only writes duty > 0, so the previous duty stays (lint LEDC_AUDIO_DUTY_ZERO, info). A ramped or modulated duty can reach 0.
  4. env, phase, attack and jitter are applied on a stop (freq < 0) LED row too — the pulse-field writes sit outside the stop/start branch, so a stop row can change the pulse shape. Observable only at the next start, and then subject to item 1.
  5. The flicker ISR tick is not monotonic across a session. The timer is deleted when no channel is left active, and the next activation re-derives the tick from the 1000 Hz floor — so the standard measurement sync marker (a 40 Hz burst, then freq -1 everywhere) resets it, and the first post-marker rate then fixes the grid for everything after it. This is why every file in sessions/test carries a "tick primer" row that keeps one invisible channel alive.
  6. The first batch is hoisted. It fires at wall-clock 0 whatever its timestamp — benign for LED (anchored to the demanded time) and not benign for audio (started at dispatch).
  7. Changing freq without restating freqR can create an accidental binaural beat. "Absent freqR" resolves to the channel's live right carrier, and the live right carrier of a mono channel equals its left one. So a later entry that moves freq and omits the freqR column leaves the right ear at the OLD pitch; the binaural-bypass test is then satisfied, so the channel plays two different carriers, beats at the size of the carrier change, and silently ignores pan. Scanning sessions/ finds 29 audibly-affected lines across four files — all of them scratch test sessions; every numbered therapeutic session writes an explicit freqR, which is why this stayed hidden. Not covered by a lint.

Backward compatibility

  • 5-token and 8-token LED lines, and 5–8-token audio lines, parse exactly as they always did. - and every trailing column are purely additive.
  • Pre-v3 files are unaffected by the v3 changes: depth is a new trailing column whose absence reproduces the old hardcoded 10 %; freqR only gains behaviour for prefixes that previously evaluated to 0.0, i.e. were broken; the absent-waveType fix only stops a reset nothing wanted; and the new sweep-path range guards only reject values the same entry would already have been refused for without a ramp.
  • The sessions/library/*.ledc set must still serialize byte-identically — that is a regression gate. Serialization re-emits - for fields the source marked unchanged, and omits a never-set trailing field.
  • The browser parser mirrors the device parser and must be updated in lockstep. As of the v3 revision its freqR is still a bare float parse and it has no depth column — the browser is behind the device on both v3 audio changes.
