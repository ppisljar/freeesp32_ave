Firmware update over the air

What you are trying to achieve: put a new firmware image on the device over WiFi, with no USB cable, and know what to do if it does not come back.

How it works, in one paragraph

The device carries two bootable programs: the main application and a small dedicated OTA updater. An update is therefore not a program rewriting itself while it runs. The main app reboots into the updater, the updater receives the new image and verifies every byte against a SHA-256 hash the browser computed before sending, writes it only if the hash matches, and then boots the main app again. The page drives all of this and tells you which step it is on.

Do not power the device off during an update. There is no other rule that matters as much. A verified image is written in one pass; an interrupted write leaves a partition in an unknown state and the recovery is a USB cable and a boot button.

Check what you are running

Open the Firmware tab. The top line reads Current firmware: 1.4.2 (built Oct 10 2026 07:21), with a second line giving the partition it booted from and the ESP-IDF version it was built with. If it says version unavailable the device is not answering — fix that before attempting an update.

Do the update

  1. Make sure nothing is playing. Press ■ STOP if in doubt.
  2. Press Image file (.bin) and pick your image. The browser immediately hashes it — the banner says Hashing image… — and then shows the SHA-256 and the file size. Compare that hash against whatever the image was published with; this is your only chance to notice you have the wrong or a corrupted file before sending it.
  3. Choose a Target:
    • Main app (ota_0) — the firmware itself. This is the usual choice.
    • Web assets (storage) — the web interface's own HTML, CSS and JavaScript. Updating this changes the page you are looking at, not the device's behaviour.
    • Configs (cfgfs) — the session library stored on the device.
  4. Press Start Update, which only becomes active once the hash is ready.
  5. Watch the banner. It walks through Requesting reboot into the updater…, Rebooting into the updater…, Waiting for the updater to come online…, then a percentage during Uploading…, then Upload complete — verifying & flashing…, Booting new firmware… and finally Update complete — the device is running the new firmware.
  6. Press Reload page so the browser picks up any new web assets.

Each wait has a 90-second budget, which comfortably covers a reboot plus rejoining WiFi. The connection sometimes drops at the very end of an app-target upload — the updater reboots the instant the image verifies — and the page recognises this, saying Connection closed after upload — the updater is likely flashing & rebooting… rather than reporting a failure.

If something goes wrong

Two buttons appear on any failure: Retry, which re-runs just the step that failed, and Start Over, which clears everything so you can pick the file again. In most failure cases nothing was written and retrying is safe.

MessageWhat it meansWhat to do
Update rejected (400): missing or malformed SHA-256 hash The updater did not get a usable hash. The app slot requires one. Press Start Over and re-pick the file so it is hashed again.
Update rejected (413): the image is larger than the target partition Wrong image, or the wrong target selected for it. Check you chose the right Target. A web-assets image is not an app image.
Update rejected (422): SHA-256 mismatch The bytes that arrived are not the bytes you sent — corruption in transit. The image was not flashed. Re-select the file and retry. If it happens repeatedly your network link is the problem; move closer to the access point.
Update failed (500): the updater could not write the partition A flash write error. Nothing was committed. Retry is safe.
Upload connection failed… The updater stayed put; you can retry. The network dropped mid-upload. The updater is still running and waiting. Retry.
Could not start the updater The device refused or did not answer the request to reboot into the updater. Some builds have no OTA support. Check the device is reachable at all; otherwise this device must be flashed over USB.
The updater did not respond on this network within 90s The updater booted but could not rejoin your WiFi, so it fell back to its own access point at a different address the page cannot reach. The device is fine. Follow the recovery steps below — the page prints them for you.
The main app did not come back within 90s. The new image may be bad… The image was flashed but does not boot, or it booted and cannot rejoin WiFi. Power-cycle once and reload the page. If it still does not return, recover over the access point below, or over USB.

Recovering over the device's own access point

When the updater cannot be reached, the page shows a block headed Updater not reachable on this network with the exact commands to run. The reason it cannot do this for you is that the access point is a different address, which browsers treat as a different site.

  1. Join the WiFi network ESP32-AVE-Setup, password entrain123.
  2. From a terminal, upload the image directly to the updater, with the hash the page showed you:
    curl -X POST --data-binary @firmware.bin "http://192.168.4.1/update?sha256=<hex>"
  3. For a web assets or configs target, add the partition to the query (part=storage or part=cfgfs) and then tell the updater to boot the app:
    curl http://192.168.4.1/reboot

Do not expect a web page at 192.168.4.1 in this state. The updater is deliberately minimal and serves only the upload endpoint — the interface you are used to is part of the main app and comes back with it.

If the device still will not boot after a bad image, the dual-boot design means the updater itself is untouched and you can reach it again by power cycling. The last resort is a USB cable and the board's boot button, which is why keeping physical access to the device matters.

Before you update: two honest caveats

  • The OTA endpoint is not authenticated. Like the rest of the device's interface, anything on your network can ask it to accept a firmware image. This is the largest remote-damage surface the device has. Keep it on a trusted network.
  • Check your settings afterwards. A new firmware may change which LED backends and audio codecs are compiled in, and it disarms any stored pin assignment it considers unsafe at boot (forcing it to -1, which silently disables that feature). If something stopped working after an update, read the device log on the Diagnostics tab and re-check Settings.
